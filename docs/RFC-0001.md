# RFC-0001：自由匿名 P2P IRC 架构

- 状态：Draft / implementation-backed
- 版本：0.4
- 所属组织：KairoteStudio
- 最后更新：2026-10-01

## 1. 定义目标

Kairc 的目标不是建立另一个中心 IRC 网络，而是提供一个可由个人运行的通信节点：本地应用继续使用简单、成熟的 IRC 接口，跨设备通信则由匿名友好的 P2P event graph 承担。

这里的“自由”有三个可测试含义：客户端可替换、节点可自托管、网络可分叉。这里的“匿名”也有明确边界：协议不要求现实身份或稳定账户；应用不主动公开本机资料；网络路径可以通过 Tor 隐藏来源。它不承诺对全局被动观察者、被攻陷终端或恶意联系人实现绝对匿名。

## 2. 参考模型

DarkFi 的 DarkIRC 证明了一个实用分层：IRC 服务器只监听本机，P2P 网络和 Event Graph 在节点间同步消息，网络 transport 与频道加密分别处理。DarkFi 文档还明确说明公开频道为明文、昵称不是现实身份、Tor 不能消除所有元数据。

Kairc 沿用这些结构原则，但使用独立的 C++23 实现和更小的首版协议。当前实现不是 DarkFi 兼容节点。

## 3. 信任边界

```text
┌──────────────┐ trusted local boundary ┌──────────────────────┐
│  IRC client  ├────────────────────────► local IRC gateway    │
└──────────────┘                         │                      │
                                         │ channel codec        │
                                         │ event validation     │
                                         │ rotating SQLite DAG  │
                                         └──────────┬───────────┘
                                                    │ encrypted frames
                                         ┌──────────▼───────────┐
                                         │ Tor/SOCKS5 or direct │
                                         │ P2P peers            │
                                         └──────────────────────┘
```

IRC 客户端和本机 `kaircd` 位于同一个信任域。P2P peers、收到的事件、数据库中同步来的字节全部不可信。

## 4. 身份

Kairc 0.4 没有账户系统。

- IRC nickname 是消息载荷中的可变 pseudonym，不证明控制权。
- 本地实现为每个事件生成新的 Ed25519 密钥，公钥只用于验证该事件内部一致性；恶意 peer 仍可主动复用自己的 key，因此它不是可信身份。
- 节点重启或连续发言不会因为签名公钥而自动关联。
- 网络连接使用持久 Ed25519 node key 认证临时 X25519 会话密钥。node key 不是聊天账户，但会让对端关联同一节点的多次连接。
- `USER` 与 realname 只用于完成 IRC 客户端握手，随后丢弃。

代价是 Kairc 不能提供“这个昵称仍是昨天那个人”的协议保证。需要稳定身份的社区可以在更高层交换签名证明，但不应把它强制成加入网络的条件。

## 5. Event Graph

时间被划分为一小时 epoch。每个事件包含：

- 协议版本与事件类型；
- network hash 与毫秒时间戳；
- 单事件 Ed25519 公钥；
- PoW nonce；
- 1–4 个同 epoch parent；
- channel tag；
- payload nonce 与 payload；
- Ed25519 signature。

每个 epoch 有由 network hash 和 epoch number 导出的虚拟 root。没有当前 tip 的事件引用这个 root。节点只有在所有非 root parent 已经提交、且 parent 属于同一 epoch 时，才能提交 event body。

事件 ID 是规范 unsigned event（包含 PoW nonce、但不含 signature）的 BLAKE2b-256 内容地址。恶意 author 即使为同一消息制造多份合法 Ed25519 signature，也只能得到同一 ID，不能复用一次 PoW 多次入库。节点重新计算 ID 后在 Ed25519 验证之前查询已存储与 pending ID，避免精确重放重复消耗验签。inventory 只发送有界数量的近期 ID，缺失事件及其 parent 通过 `GET_EVENTS` 递归获取。

每个已提交 event 的 canonical layer 为最长 parent 路径长度；历史按 `(epoch, layer, event ID)` 排序，因此各节点在拿到相同事件集合后收敛到相同顺序。实时消息只使用短呈现窗口，晚到和分区恢复消息通过 IRCv3 timestamp/batch/replay 标签明确标识，而不是伪装成实时强时序。

缺 parent event 由 parent→children 索引驱动，只重查相关后代，并受 global、per-peer 与 receipt TTL 约束。默认保留 24 个小时 DAG。删除完整旧 epoch 不破坏新 epoch 的 parent closure。

## 6. 匿名抗滥用

没有账户意味着无法按账户限流。当前版本要求事件 hash 满足配置的前导零位数，相当于一个简化 Hashcash。它满足：

- 验证成本远低于生成成本；
- 不需要中心身份；
- 难度属于网络参数，异构难度的节点不会互通事件。

它不提供公平性，也不能阻止 GPU/ASIC 或大型 botnet。因此 0.4 不把 PoW 当作资源上限：已认证 peer 同时受每 identity 和进程级 bytes/frame/event token bucket、固定验证工作池、pending 配额与持久化配额约束。

未来协议可以引入 RLN 或其他匿名凭证证明，但必须先给出独立 RFC、公共参数生命周期、membership root、nullifier/double-signal 处理、匿名撤销和恢复流程；在电路与 verifier 完成审计之前不能用“RLN”标签包装普通 rate limit。

## 7. 频道隐私

公开频道 tag 从 network 与 canonical channel name 派生，载荷为明文。私密频道 tag 从 network 与共享密钥派生，载荷使用 XChaCha20-Poly1305 加密。AEAD associated data 绑定 version、kind、network、timestamp、一次性 author key、parents 和 channel tag；攻击者不能把截获的密文包装进自己签名的新事件来重复投递。

共享密钥频道隐藏 nickname 和 message body，但不隐藏：

- 稳定的频道 tag；
- event 时间、大小、parent 和传播路径；
- 参与节点的在线时序；
- 拥有密钥的恶意成员观察到的信息。

替换共享 secret 会生成新的 channel tag，因此保留成员可以通过带外渠道协调一次密钥代际轮换，并停止向被移除成员分发新 secret。这个流程需要重启、不能自动协商、不能防回滚，也没有 per-message sender ratchet；任何单一代际密钥泄漏都会暴露该代际保存的历史。未来多人密钥协议不能在未完成密码学评审前标记为“安全群聊”。

## 8. P2P transport

P2P v3 由 server 先发送包含 network 与 fresh random cookie 的固定 prelude；client hello 必须把 cookie 签进 challenge。Hello 还包含 network、client/server role、持久 Ed25519 public key 与临时 X25519 key，并由持久 node key 签名。默认只接收配置在 `trusted_peer` 中的身份。Server 在有界非阻塞 cookie/hello 状态机中完成 cookie、固定字段和 allowlist 预检，再进入有界验签槽；只有签名通过并通过每 identity/全局握手预算后，才生成本地临时 key/签名。通过 libsodium `crypto_kx` 派生方向独立会话密钥后，双方以 AEAD 相互确认按 client/server 固定顺序组成的 transcript，确认成功才进入 ready 状态。每个普通 frame 使用从 1 开始的递增 nonce 和 XChaCha20-Poly1305，并设置 1 MiB 上限。

这能防止被动链路观察者读取 frame、检测 frame 篡改，并在 key 被 pin 时阻止主动中间人冒充对端。签名事件仍提供独立内容完整性；私密频道 payload 还有独立的端到端密钥。显式设置 `allow_unknown_* = true` 会放弃 peer allowlist，但不会隐藏或替代持久身份。

匿名网络默认路径应为 Tor onion service。`tcp://` 是开发和受控网络 transport，不是匿名模式。

节点发现是 P2P v3 内的轻量 Kademlia 子协议。持久 node key 对短期、单 onion endpoint record 签名；record 带 network、单调 sequence、TTL、capability 和撤销 tombstone。节点只有在连接该 onion endpoint 且握手返回完全相同 identity 后才传播 live record；只有曾完成该验证的 identity 才能传播 tombstone。最高 sequence、digest、验证 anchor 与独立 watermark 持久化，目录淘汰或重启不能在旧 record 仍有效时回滚。

`trusted` discovery 把 subject 和 link 都限制在运营者 allowlist；`open` discovery 接受任意自签 identity。XOR bucket、request/session 上限、可信记录优先、退避与轮换控制本地成本，但签名不提供身份稀缺性，因此 open 模式仍可被 Sybil 填充 bucket 或 eclipse。静态 pinned bootstrap 仍是初始 rendezvous 和信任配置的一部分。

## 9. 自由与治理

自由不是单一运营者的“无规则公共房间”。Kairc 把治理下放：

- 节点可以选择 peers、retention、PoW 与本地可读频道；
- 私密频道的密钥由成员自己控制；
- 任意网络可以使用新的 `network_id` 独立分叉；
- 过滤和客户端呈现属于本地策略，不由中心服务强制；
- 核心网络不设置全局昵称、中心封禁表或不可退出的服务条款。

0.4 尚未实现可传播的 moderation event。加入前必须先定义其权限来源、撤销和滥用边界。

## 10. 安全不变量

1. 未通过签名、network、PoW、大小与时间检查的事件不得进入 store。
2. 非 root parent 不完整时，event body 只能进入有界 pending queue。
3. 一个 epoch 的事件不得引用其他 epoch 的 parent。
4. P2P frame、inventory、event、IRC line、pending queue、per-peer pending、本地频道表、连接槽位、验证并发、传输速率和持久存储都有硬上限。
5. 私密频道认证失败时不得尝试把 ciphertext 当成公开消息解析。
6. 私密 ciphertext 必须认证其签名事件上下文，不能在另一个事件外壳中复用。
7. IRC listener 不得绑定非 loopback 地址。
8. SOCKS5 必须把域名交给 proxy，不能预先执行本地 DNS 查询。
9. 应用默认日志不得包含 peer address、nickname 或 message body。
10. P2P session 只有在 peer hello 签名、信任策略和 transcript confirmation 全部通过后才能进入 ready 状态。
11. 各节点对同一完整 event set 的持久历史顺序必须收敛；无法保证实时顺序时必须显式标记 replay。
12. 一个 unsigned event 无论有多少份合法 signature 都只能对应一个 Event ID 和一次 PoW 成果。
13. 未完成 exact-identity onion endpoint 握手的 peer record 不得作为可传播 live route；未被该验证锚定的 tombstone 不得占据或传播到路由响应。
14. Peer record 的 durable sequence watermark 不得因 raw route 过期、目录容量、进程重启或短 TTL 更新而提前丢失。

## 11. 里程碑

### 0.4：当前原型

- C++ event graph、签名、PoW、SQLite parent closure；
- 本地 IRC gateway；
- 认证并加密的 P2P v3 frame、静态可信 peer、Tor SOCKS5；
- 公开与共享密钥频道；
- early dedup、传输/验证/pending/磁盘配额；
- canonical DAG history 与 IRCv3 replay 呈现；
- 签名 onion peer record、pinned bootstrap、轻量 Kademlia lookup、持久撤销/高水位和三节点 bootstrap 消失后的发现传播测试；
- ASan/UBSan、TSan CI 和双节点加密传播测试。

### 0.5：可测试匿名网络

- bootstrap/operator diversity、抗 eclipse bucket 策略与可审计的 onion-service lifecycle；
- header-first / range sync 与更严格的字节 metering；
- RLN/匿名凭证 proof 接口与可复现公共参数；
- 自动成员密钥代际、撤销与 sender ratchet 设计；
- 覆盖 parser 与 wire format 的持续 fuzzing 和故障注入测试；
- onion service 运维手册。

### 1.0：公开网络候选

- 独立密码学与协议安全审计；
- 至少三个独立 seed/operator；
- 参数升级、数据库迁移和灾难恢复流程；
- 可复现构建和稳定 wire version；
- 明确的漏洞响应与版本支持政策。
