# RFC-0001：Kairc 的产品边界与网络架构

- 状态：Draft
- 目标版本：0.1 → 1.0
- 所属组织：KairoteStudio
- 最后更新：2026-10-01

## 摘要

Kairc 是一个受早期 IRC 启发、优先支持开放协议与自托管的实时通信系统。第一阶段提供兼容 IRC 客户端的单节点服务器；第二阶段补齐公共服务所需的身份与治理；第三阶段才实验节点互联。

这份 RFC 的作用不是一次性定义所有 wire format，而是先固定那些以后很难推翻的产品边界和安全不变量。

## 为什么值得做

今天的群聊产品通常把协议、客户端、身份、历史数据和运营权绑在同一个平台里。IRC 的早期模型证明了另一条路：服务器只负责实时路由，客户端可以自由选择，频道是轻量的公共空间，网络能够由不同运营者共同组成。

Kairc 不复刻 1988 年的全部限制。它继承可替换和可自托管的结构，同时把加密传输、资源限制、可审计实现和滥用治理当作核心能力。

## 目标

- 普通 IRC 客户端无需专用插件即可加入单节点网络。
- 一台低配置机器能够运行一个有明确资源上限的公共节点。
- 默认不产生永久聊天档案。
- 核心协议和官方实现均可独立演进，客户端不被某个 Web UI 锁定。
- 将来互联时，一个失陷节点不能伪造其他节点已经签名的事件。
- 节点断开和恢复不会制造无限广播环路。

## 非目标

- v0.1 不做类似 Discord/Slack 的完整工作区产品。
- v0.1 不实现端到端加密；TLS 只保护客户端到节点的链路。
- v0.1 不声称去中心化或联邦化。
- 不做推荐流、关注者算法或广告画像。
- 不保证未选择持久化的消息可以恢复。

## 系统分层

```text
┌───────────────────────────────────────────┐
│ Clients: terminal / desktop / web gateway │
└───────────────────┬───────────────────────┘
                    │ IRC over TCP/TLS
┌───────────────────▼───────────────────────┐
│ Node                                      │
│  protocol parser → policy → room hub      │
│                         ├─ ephemeral state│
│                         └─ optional store │
└───────────────────┬───────────────────────┘
                    │ future link protocol
┌───────────────────▼───────────────────────┐
│ Peer nodes with independent local policy  │
└───────────────────────────────────────────┘
```

### 协议层

负责 IRC 消息解析、512 字节线长限制、命令与 numeric 响应。它不直接拥有频道状态，也不访问存储。

### Hub 与策略层

单节点内的昵称、频道、成员与 operator 状态由一个 owner 串行修改。连接 goroutine 只能提交命令和接收有界消息队列，不能直接修改共享状态。

### 存储层

v0.1 没有消息存储。未来即使加入存储，也必须满足：

- 每个频道显式开启，而非全局默认开启；
- retention 可配置且有硬上限；
- 客户端能够从协议响应中知道当前频道是否记录历史；
- 删除策略和备份策略由节点公开说明。

### 节点互联层

节点互联不能直接复用客户端 IRC 命令。未来 link protocol 至少需要：

- 每节点独立的 Ed25519 身份密钥；
- 包含来源、房间、单调序列和时间的签名事件；
- 全局唯一事件 ID 与去重窗口；
- hop limit 或等价的环路抑制机制；
- 明确的房间归属、operator 授权和冲突解决规则；
- 断线后的有界补发，不能无限复制全部历史；
- 协议版本与 capability negotiation。

在这些约束形成单独 RFC 并完成威胁建模前，不合并“临时版服务器互联”。

## 身份模型

v0.1 的昵称是单节点、连接生命周期内的临时标识。大小写按 RFC 1459 casemap 比较，断开后释放。

v0.2 可以增加账户，但账户与展示昵称必须分离：

- 账户是权限主体；
- 昵称是可变展示名；
- 未登录用户仍可由节点策略允许进入公共频道；
- 认证优先采用 SASL，不在自定义命令里传明文密码。

跨节点的全局昵称唯一性不是目标。需要稳定引用时，应使用 `account@node` 或密码学主体 ID。

## 频道与治理

- 第一个进入新频道的人获得 operator。
- 频道至少维持一个 operator；最后一位 operator 离开时，节点确定性选择继任者。
- 默认启用 no-external-message 与 topic-lock 语义。
- 节点运营者保留断开恶意连接和执行本地封禁的最终权力。
- 联邦频道必须接受各节点可能执行更严格的本地策略，不能要求最弱策略覆盖全网。

## 安全不变量

1. 任意一条客户端输入最多占用有界内存。
2. 慢速接收者不能阻塞整个 hub。
3. 未加入频道的客户端不能向该频道发送消息。
4. 用户提供的文本不能注入额外 IRC 行。
5. 昵称索引与频道成员状态在并发连接下保持一致。
6. 公网部署必须使用 TLS 或可信 TLS 终止代理。
7. 未经认证的节点事件永远不能获得远端 operator 权限。

## 滥用与隐私

“不保存消息”不能代替治理。公开节点至少需要连接限流、IP 级限制、昵称/频道封禁、operator 工具、事件日志与举报渠道。日志应记录运营所需的最少元数据，并公布保留期。

v0.1 已有每连接限流、有界队列、连接上限和频道 operator；IP 级限制、封禁与审计日志属于 v0.2 上线公共节点前的阻断项。

## 版本里程碑与验收条件

### v0.1：单节点

- 至少与 WeeChat、irssi 和一个 GUI 客户端完成互操作测试；
- parser、频道消息、昵称冲突和 operator 生命周期有自动化测试；
- race detector、vet 和容器构建进入 CI；
- 公布支持命令与已知限制。

### v0.2：可运营公共节点

- SASL 与账户权限；
- K-line/频道 ban/invite/key 的最小集合；
- Prometheus 指标与结构化审计事件；
- 可选、可见、有 retention 上限的消息历史；
- WebSocket gateway 与参考 Web 客户端；
- 完成一次针对单节点的威胁模型与安全评审。

### v0.3：互联实验

- 单独的 link protocol RFC 和测试向量；
- 三节点拓扑下验证去重、分区、重连与权限冲突；
- 节点密钥轮换和吊销流程；
- 对恶意或失陷 peer 的隔离测试。

### v1.0：稳定网络

- 至少三个独立运营方；
- 公开兼容性与迁移承诺；
- 第三方安全审计；
- 灾难恢复和协议升级演练。

## 待决问题

- 项目正式中文名是否使用“刻聊”、音译名，还是只保留 Kairc？
- 首个公共节点的域名和运营主体是什么？
- v0.2 历史存储选用嵌入式 SQLite，还是保持外部存储接口？
- link protocol 是自研最小协议，还是桥接 IRCv3/Matrix 生态？
- 公开节点允许完全匿名连接，还是要求经过验证的临时凭据？
